# Backend — Booking Service

> NestJS API для платформы бронирования. Обрабатывает жизненный цикл бронирований, платежи через Stripe, аутентификацию Better Auth и email-уведомления.

## Stack

- **Runtime:** Node.js 20+, NestJS (strict TypeScript)
- **Database:** PostgreSQL on Neon (Prisma ORM)
- **Cache/Session:** Upstash Redis (Better Auth secondary storage)
- **Auth:** Better Auth (Prisma adapter)
- **Payments:** Stripe (Test Mode)
- **Email:** Resend
- **Deploy:** Render (Free Tier — cold starts ~60s)

## Project Structure

- `src/modules/` — NestJS feature modules (`bookings`, `auth`, `payments`, `notifications`)
- `src/common/` — shared DTOs, guards, interceptors, filters
- `src/core/` — Prisma service, config validation, AppModule
- `prisma/` — schema, migrations, seed scripts
- `.env.example` — reference for all required environment variables

## How to Work Here

### Verification Loop

After **any** non-trivial edit, run in this order and fix failures before moving on:

1. `npm run lint`
2. `npm run test`
3. `npm run build`

Do not report a task complete until all three pass. If a test fails because of changed behavior, update the test in the same edit — do not leave the suite broken.

### Database Safety (NON-NEGOTIABLE)

- **Never run `prisma migrate reset`** without explicit confirmation from the user. Prisma enforces this for AI agents via `PRISMA_USER_CONSENT_FOR_DANGEROUS_AI_ACTION` — surface the prompt, do not set the variable yourself[citation:3].
- Scratch work gets a **throwaway Neon branch**, not the shared dev database. If you need to test a migration or query safely, ask the user to create a Neon branch, or use `prisma migrate diff` to rehearse.
- All DB access goes through `PrismaService`. Direct `PrismaClient` instantiation in a module is forbidden.
- Never edit existing migration files. Create a new migration.

### Better Auth Conventions

- Better Auth config lives in `src/modules/auth/auth.config.ts`. The Prisma adapter is wired there.
- **Prisma version lock:** this project pins `better-auth` at **1.4.6** due to peer-dep constraints with Prisma 5.x. Do not upgrade either package without running the full test suite and verifying session creation/validation manually.
- Redis (`secondaryStorage`) stores sessions, not the database. When a session-related bug appears, check Redis key TTL and connectivity before touching Prisma.
- `user` and `session` are generated by Better Auth. Do not hand-edit those Prisma models — run `npx @better-auth/cli generate` if the schema needs updating[citation:12].

### Stripe Patterns

- Stripe is **always** in Test Mode in this repo. Live keys must never appear in `.env` or any config.
- Webhook handlers live in `src/modules/payments/stripe.webhook.controller.ts`. **Verify the signature before any processing.** Use `stripe.webhooks.constructEvent` with the raw body — do not parse JSON first.
- All Stripe calls go through a single injectable `StripeService`. No `new Stripe(...)` scattered across controllers.
- Idempotency: every Stripe mutation (create checkout session, refund, etc.) must use an idempotency key derived from the booking ID or a UUID. Do not retry without the same key.

### Email (Resend)

- All outbound email goes through a single `EmailService` in `src/modules/notifications/`.
- **Daily quota: 100 emails/day.** Never send in a loop without batching or a rate limiter. If a test needs to verify email sending, mock `EmailService` — do not fire real emails.
- Use Resend's `idempotencyKey` for transactional emails (booking confirmation, cancellation) to prevent duplicates on retry[citation:19].
- Never put user-supplied HTML into an email body without sanitization.

### DTO Validation

- Every DTO uses `class-validator` decorators. No `any` in DTO types.
- Global `ValidationPipe` is configured with `{ whitelist: true, forbidNonWhitelisted: true }` in `main.ts`. Do not weaken these settings.

### Error Handling

- Throw NestJS HTTP exceptions (`NotFoundException`, `BadRequestException`, etc.) at service/controller boundaries. Never leak raw Prisma or Stripe errors to the client.
- Use the global exception filter in `src/common/filters/` for consistent error shapes.

## Environment Variables

All env vars are validated at startup with `@nestjs/config` + Joi/Zod schema in `src/core/config/`. If you add a new env var, update both `.env.example` and the validation schema. `process.env` access outside the config service is a lint warning.

Required vars (reference only — never hardcode):

- `DATABASE_URL` (Neon — **must include `?sslmode=require`**)
- `REDIS_URL` / `UPSTASH_REDIS_REST_URL` (Upstash)
- `BETTER_AUTH_SECRET`
- `STRIPE_SECRET_KEY` (sk_test_...)
- `STRIPE_WEBHOOK_SECRET`
- `RESEND_API_KEY`

## Commands

```bash
npm run dev              # start with hot reload
npm run build            # compile to dist/
npm run lint             # eslint + prettier check
npm run test             # jest unit tests
npm run test:e2e         # e2e tests

npx prisma migrate dev --name <description>   # create + apply migration
npx prisma generate                             # regenerate client after schema change
npx prisma studio                               # browse data (read-only is fine)
```
